Point it at a repository. Get a website, not a plan.

landing-page reads what your code actually implements — not what the README claims — then builds a real landing-page site from that evidence, runs it, looks at it at three screen widths, and fixes what's broken before it hands the work back.

Real source files, a design system derived from your product, working navigation, build scripts, and a deployment path. The README it writes afterward is one short page that links to the site.

EVIDENCE CLASSIFICATION the tier chooses the verb
Confirmed

“Runs entirely offline and exposes a documented HTTP API.”

Implemented, backed by code, tests, config, or current docs. Say it plainly.

Partial

“Includes experimental support for Postgres.”

Present but incomplete, unstable, gated, or lightly tested. The qualifier stays in.

Planned

“Multi-tenant deployments — planned.”

Only in a roadmap, an issue, a spec, or a placeholder. Never presented as available.

Unverified

Cut from the page.

Suggested but not adequately supported. It doesn't get a sentence.

Why the usual answer disappoints

Ask most tools for a landing page and you get one of three things back. This skill is written against all three.

A restyled README

Your README's paragraphs, chopped into cards. It reads like documentation with a gradient on it, and it sells nothing. The skill treats the README as one input — usually the least current one — and goes to the implementation instead.

A design proposal

Wireframes, a palette, a section outline, and a suggestion that you build it. The skill is an implementation agent: create the files, run the project, look at the result, fix the defects, repeat until polished.

Confident fiction

Invented user counts, imaginary testimonials, “enterprise-grade” applied to a prototype. Every claim is classified against repository evidence first, and the tier decides the wording.

Seven phases, worked in order

SKILL.md carries the protocol. Five reference files are opened only at the phase that needs them, so the model isn't reading a design checklist while it's still reading your source tree.

  1. Investigate

    Reverse-engineer the real product from code, schemas, migrations, CI, tests, docs and live TODOs: identity, audience, capability inventory, and the maturity the evidence actually earns. Capabilities that exist in the implementation but appear nowhere in the docs get elevated; documented features backed by a stub get qualified.

    references/investigation.md
  2. Assess the stack — before any design work

    Find the existing site, design system, or brand. If the repository already declares tokens, brand colors, or typefaces, that is the product's visual identity and the site inherits it. Then pick the lightest stack that can look genuinely good, and decide where the site lives.

    references/stack.md
  3. Position

    Settle on one category, one audience, one problem, one differentiator, one value proposition, three to six capability themes, and two calls to action — before a word of copy is written.

  4. Design

    Write the design system down first: color, type, space, form, behavior, detail. Derive it from the software's own domain rather than a template — and spend boldness once, in a single place, with everything around it kept quiet.

    references/design.md
  5. Build

    Section structure, scroll narrative, visual rhythm — implemented as real source files with semantic HTML, reusable sections, and no dependency sprawl.

    references/structure.md
  6. Verify

    Run it. Render it. Inspect at desktop, tablet and mobile widths. Fix the clipping, the contrast, the dead links, the broken mobile menu. Build it and preview the built output too, so asset paths still resolve under a repository subpath. If no renderer is available, the skill has to say so rather than imply it looked.

    references/review.md
  7. Rewrite the README

    Last, and short: a technical entry point that links to the site, with verified commands and an honest project-status line. Never a second copy of the website.

What it will not write

A landing page is the one document where exaggeration is traditional. These are hard exclusions in the skill, not suggestions — if the repository doesn't support it, it doesn't reach the page.

  • Customer counts, usage numbers, star counts, adoption claims
  • Testimonials, customer logos, awards, press mentions
  • Benchmarks and performance numbers that were never measured
  • Uptime, reliability, or security guarantees
  • Production deployments and enterprise readiness that aren't in evidence
  • Roadmap dates and release timelines
  • Stock photography and fabricated screenshots
  • Dead placeholder links in the rendered page

It also picks the maturity word the evidence earns — prototype and early-stage are available words — judged on test depth, release history, upgrade paths, error handling, observability, deployment automation, and unfinished UI. Polish is not maturity.

Install

Copies SKILL.md and the five reference files into ~/.claude/skills/landing-page/. Re-run to update; uninstall by deleting the folder.

Windows — PowerShell

iwr -useb https://raw.githubusercontent.com/scottconverse/landing-page/main/install.ps1 | iex

macOS / Linux

curl -fsSL https://raw.githubusercontent.com/scottconverse/landing-page/main/install.sh | bash

Manual

git clone https://github.com/scottconverse/landing-page
# copy SKILL.md and references/ into ~/.claude/skills/landing-page/

Then say any of this

  • /landing-page
  • build a landing page for this repo
  • make this repo look legit
  • what does this project even do?
  • write the pitch for this repo

It also triggers on its own before a repository is announced, open-sourced, or released.
